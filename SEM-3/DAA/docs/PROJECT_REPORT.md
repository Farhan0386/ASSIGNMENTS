# Mini-Courier Planner: Capstone Project Report

**Course outcome mapping:** CO1-CO5 (as stated in the assignment brief)  
**Project type:** Integrated algorithm prototype  
**Measurement note:** Runtime values below are observations from the execution environment and vary by machine.

## Abstract

This project combines stable merge sort, 0/1 knapsack dynamic programming, Dijkstra shortest paths, and a nearest-neighbor traveling-salesperson heuristic in a modular Python courier-planning application. Given parcel priority, deadline, weight, destination, vehicle capacity, and a weighted road graph, it selects a high-priority feasible batch and creates a closed delivery tour whose road distance is evaluated over shortest paths. The example selects three parcels of total weight 15 and priority score 28, and returns a 22 km route. Tests and deterministic generated benchmarks provide correctness and runtime evidence.

## 1. Problem statement and scope

A courier has one vehicle trip with a limited weight capacity, a set of parcels, and customers located on a road network. The planner should rank parcels, select a valuable feasible batch, compute shortest road paths, and propose an ordered delivery tour. This implementation is an educational prototype: it does not model live traffic, service durations, time-window feasibility, multiple vehicles, or stochastic travel time. Deadlines participate in ranking after priority, rather than hard feasibility constraints.

## 2. Design and data model

`Parcel` stores a unique ID, destination node, positive integer weight, ISO-style deadline text, and nonnegative integer priority score. The input JSON separates parcels and vehicle capacity from a route JSON containing a depot, unique node IDs, and undirected weighted edges. Edge distances are finite and nonnegative. An adjacency list supports sparse graphs. The planner validates references and reports unreachable destinations.

Pipeline: (1) sort all parcels by decreasing priority, earlier deadline, then ID; (2) use 0/1 DP to maximize the sum of priority scores under capacity; (3) run Dijkstra from the depot and retain shortest paths; (4) construct distances among selected stops from shortest road paths; (5) greedily visit the closest remaining stop and return to depot; (6) expand each leg into actual graph nodes and report component timings.

## 3. Algorithms and justification

| Stage | Method | Complexity | Reason |
|---|---|---|---|
| Prioritization | Stable merge sort | O(n log n) time, O(n) auxiliary space | Predictable bound and transparent tie ordering |
| Capacity selection | 0/1 knapsack DP | O(nW) time and space | Finds maximum total priority for integer capacity W |
| Shortest paths | Heap-based Dijkstra | O((V+E) log V) | Nonnegative road distances; efficient on sparse networks |
| Multi-stop route | Nearest-neighbor TSP heuristic | O(k²) after pairwise distances | Simple scalable baseline; does not guarantee an optimal tour |

Knapsack uses priority as value, not a priority-to-weight ratio; therefore it solves the stated batch objective exactly for integer weights. The route heuristic operates on the metric closure induced by shortest road paths, so every chosen leg is a feasible shortest route in the original graph. The closed tour includes the return to depot. A destination shared by multiple selected parcels appears once.

## 4. Sample result

The supplied dataset contains eight parcels, eight road nodes, and vehicle capacity 15. The selected batch is P-102 (B, 7, score 12), P-103 (C, 5, score 10), and P-105 (E, 3, score 6): total weight 15 and total priority 28. Depot shortest paths are DEPOT-B = 6 km, DEPOT-B-C = 8 km, and DEPOT-B-C-D-E = 11 km. Nearest-neighbor stop order is DEPOT -> B -> C -> E -> DEPOT, expanded road path is DEPOT -> B -> C -> D -> E -> D -> C -> B -> DEPOT, and closed-tour distance is 22 km. The console trace is in `results/sample_run.txt`.

The priority ranking is deterministic: P-102, P-106, P-103, P-104, P-101, P-108, P-105, P-107. Ranking is an ordering for review; the knapsack optimizes total score and is not constrained to select a prefix of that list.

## 5. Correctness evidence

Seven automated unit/integration checks cover sorting order and input preservation, optimal feasible knapsack selection, invalid capacity rejection, an indirect shortest path, unreachable-node reporting, an empty tour, and the complete sample pipeline including capacity, stops, and route distance. Run `python -m unittest discover -s tests -v`. The reference sample trace is generated by `python -m src.main`.

## 6. Performance experiment

The benchmark uses a fixed seed to create a connected path backbone plus random shortcuts and synthetic parcels. Each component is measured five times; the median is written to `results/benchmark_results.csv`. The full planner is timed as an integrated stage and includes sorting, knapsack, shortest paths, and route planning. Run `python -m src.benchmark` to regenerate the CSV and `images/runtime_benchmarks.png`.

| Parcels/nodes | Sorting (ms) | Knapsack (ms) | Dijkstra (ms) | Full planner (ms) |
|---:|---:|---:|---:|---:|
| 20 | 0.0274 | 0.2873 | 0.0248 | 0.9286 |
| 50 | 0.0855 | 1.6780 | 0.0497 | 5.8123 |
| 100 | 0.1913 | 7.3606 | 0.1058 | 23.0891 |
| 200 | 0.4294 | 31.0595 | 0.2395 | 105.6610 |

These are single-machine medians and should not be compared across hardware without a controlled environment. The increasing knapsack and route-planning times reflect the pseudo-polynomial capacity table and the pairwise distance work/nearest-neighbor steps; sorting and a single Dijkstra run are small at these sizes. For larger cases, consider a compact one-dimensional knapsack table with predecessor reconstruction, bitset or approximation methods where justified, computing only necessary stop-to-stop shortest paths, improved route heuristics (2-opt), and profiling before optimization.

## 7. Limitations, future scope, conclusion

The model uses integer weights and scores, static symmetric distances, one vehicle, and a greedy route approximation. It does not guarantee globally optimal routing. Practical extensions include multiple trips/vehicles, time-window constraints, loading priorities, asymmetric or time-dependent roads, route improvement with 2-opt, and validation against a trusted solver on small graphs. The project demonstrates a complete modular flow and makes algorithm assumptions visible so the output can be explained in a demonstration or viva.
